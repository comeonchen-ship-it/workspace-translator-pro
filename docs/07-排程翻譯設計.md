# 07 — 排程翻譯（Scheduled / Batch Translation）設計規劃

> 狀態：**規劃中，尚未實作。** 本文件只做設計，不含任何功能程式。
>
> **目標一**：讓使用者「一次選好來源、目標語言、目的地、時間」，之後由系統
> 自動把檔案**扇出（fan-out）翻譯成多個語言**並整齊歸檔，減少逐檔手動操作。
>
> **目標二（同等重要，呼應你的要求）**：把整個功能做成**可加掛的獨立模組**，
> 新增「來源型態 / 目的地策略 / 命名規則 / 排程型態」時只改**註冊表資料**，
> **不動翻譯核心、不動全域參數**。爆炸半徑控制在 🟢，只有極少數必要接點是 🟡。
>
> 先讀 [02-影響範圍地圖](02-影響範圍地圖.md)（🔴/🟢 的定義）與
> [06-多語系介面設計 §10](06-多語系介面設計.md)（「用註冊表做擴充」的範式）——
> 本設計沿用同一套哲學。

## 一、為什麼要這個功能：實用場景

### 企業場景

| # | 場景 | 需求本質 | 對應設計元件 |
|---|---|---|---|
| E1 | **全球製造業**：一份作業標準書（SOP）要同時給墨西哥廠(es)、越南廠(vi)、泰國廠(th)、蘇州廠(zh-CN) | 1 份來源 → **N 個語言**扇出 | 多目標語言 + 統一目的地 |
| E2 | **HR／法遵**：員工手冊每季更新，要重新產出所有員工語言版本 | **來源變更 → 自動重跑**，週期性 | 週期排程 + 「只翻改過的檔」 |
| E3 | **行銷**：一個資料夾裡的產品單頁，夜間批次翻譯當天新增的檔案 | **整個資料夾**批次 + 離峰執行 | 資料夾來源 + 定時排程 |
| E4 | **教育訓練**：新人 onboarding 簡報要在地化給各區團隊 | M 份 × N 語言的矩陣 | 多來源 × 多目標 |
| E5 | **合規／安全公告**：新公告發布後 X 小時內須備妥所有工人語言版本 | 事件觸發、時限內完成 | 觸發式（Phase 3） |

### 個人場景

| # | 場景 | 需求本質 |
|---|---|---|
| P1 | 自由譯者／老師：把檔案丟進「待翻譯」資料夾，**過夜批次**翻好 | 資料夾來源 + 延後執行（避開白天、分散 API 用量） |
| P2 | 學生：把一組研究文件翻成母語 | 多來源一次選、單一目標語言 |
| P3 | 內容創作者：一份文件翻成 3 種語言給不同受眾 | 1 → N 扇出，立即執行 |
| P4 | 社團／家庭：共用文件更新時自動翻譯 | 來源變更觸發 |

### 從場景蒸餾出的共同需求

1. **扇出（fan-out）**：1 份來源 → 多個目標語言（幾乎每個場景都要）。
2. **批次（batch）**：一次處理多份檔案，最好能「選整個資料夾」。
3. **統一歸檔**：輸出集中到指定資料夾，最好能**依語言分子資料夾**、命名一致。
4. **時間控制**：立即 / 指定時間 / 週期 / 來源變更時。
5. **只做增量**：週期性重跑時，只翻「新的或改過的」檔案，省錢省時。

> 觀察：**「扇出 + 批次 + 歸檔」是所有人都要的核心；「排程時間」是加分項。**
> 因此設計上把兩者拆開——先能一次把一份檔案翻成 8 種語言並歸好檔（無排程），
> 再疊上排程。這也決定了分期順序（見第九節）。

## 二、三個繞不開的技術現實（先講清楚，才不會設計出做不到的東西）

### C1. Manifest V3 的 Service Worker 隨時會被回收

排程的本質是「未來某時刻自動執行」，但 MV3 的背景程式沒有常駐保證
（見 [05-已知問題 H3](05-已知問題與技術債.md)）。

**對策**：
- 用 `chrome.alarms`（需在 manifest 加 `"alarms"` 權限）當「鬧鐘」喚醒 SW，
  **不能**用 `setTimeout`（SW 一死就沒了）。
- 每個排程任務的狀態全部寫 `chrome.storage.local`，SW 重啟後能從 storage 重建。
- 大批次要**可續傳**：記錄「這個 job 已完成到第幾個檔案 / 第幾個語言」，
  中斷後從斷點續跑，而不是整批重來。

### C2. 現在的 OAuth 拿不到 refresh token —— 這是最關鍵的分期閘門

現況是 Implicit Flow（`response_type=token`，[background.js:603](../background.js:603)），
access token 約 1 小時、**沒有 refresh token**（見 [05-已知問題 H2](05-已知問題與技術債.md)）。

**推論（很重要）**：

| 排程情境 | 現況做得到嗎？ |
|---|---|
| 使用者在場、瀏覽器開著、近 1 小時內授權過 → 立即批次翻譯 | ✅ 可以 |
| 排定 10 分鐘後、瀏覽器仍開著 | ✅ 可以（token 仍有效或可靜默續取） |
| 排定**明天半夜**、使用者不在、瀏覽器可能關著 | ❌ **做不到**。token 早已過期，且無法在無人時彈出登入視窗 |

**結論**：**真正的「無人值守／瀏覽器關閉也能跑」的排程，前置條件是把認證升級成
Authorization Code Flow + PKCE 以取得 refresh token**（[05-已知問題 H2](05-已知問題與技術債.md) 的長期修法）。

因此本設計採「**能力分級**」：
- **Phase 1–2**（本文件重點）：只支援「**瀏覽器開著時**」執行的批次與近期排程。
  在場即可，不需要動 OAuth。這已能滿足 E1／E3／E4／P1–P3 的絕大多數需求。
- **Phase 3**：無人值守的週期排程，**以 OAuth 升級為前置**，獨立立項。

> 這個限制要在 UI 上**誠實呈現**：排程時間若超出目前 token 的有效範圍，
> 就顯示「需要瀏覽器保持開啟」或「需要重新授權」，而不是讓使用者以為半夜會自動跑、
> 結果早上發現沒跑。

### C3. 現有流程假設「有一個當前分頁」

`startTranslation` 目前會帶 `tabId`，用於分頁關閉時取消任務
（[background.js](../background.js) 的 `registerTabMapping`）；進度也只推播給「正在看該檔的側邊欄」。

排程翻譯的檔案**不會開在分頁裡**。所以需要一條 **headless（無分頁）執行路徑**：
- 允許 `tabId` 為 `null`；不建立分頁映射。
- 進度不推給某個分頁，而是寫進 job 狀態，由「排程面板」讀取顯示。
- 完成後**不自動開分頁**（批次 20 個檔案不可能開 20 個分頁），改為在 job 結果列出連結。

好消息：**翻譯核心本身其實是 tab-independent 的**——它靠 file ID + Drive/Slides/... REST API 運作，
不需要分頁。只有外圍的通知/取消/開分頁邏輯假設了分頁。所以 C3 是「加一條旁路」，不是重寫。

## 三、整體架構：排程器是「任務產生器」，不是新的翻譯引擎

**核心設計原則：排程器不翻譯，它只是把一份批次規格展開成一堆既有的佇列任務。**

```
┌─────────────────────────────────────────────────────────────┐
│  新增模組（獨立，🟢）         scheduler/                      │
│                                                              │
│  ①  Job Builder（UI）  ── 使用者定義一個 Job：                │
│         來源 + 目標語言[] + 目的地 + 命名 + 排程              │
│                     │ 存成 scheduleJobs[]（新 storage key）   │
│                     ▼                                         │
│  ②  Scheduler（chrome.alarms 驅動）                           │
│         到點 → 讀 Job → 呼叫 Expander                         │
│                     ▼                                         │
│  ③  Expander（純函式）                                        │
│         把 1 個 Job 展開成 N 筆「單檔單語言」工作項            │
│         （來源檔案清單 × 目標語言，套用目的地/命名規則）        │
│                     ▼                                         │
│  ④  Dispatcher                                               │
│         每一筆工作項 →  requestTranslationStart(...)          │
│                        （★ 既有佇列入口，完全重用）           │
└──────────────────────────────┼──────────────────────────────┘
                               │ 重用，不修改
                               ▼
┌─────────────────────────────────────────────────────────────┐
│  既有核心（🔴，本功能盡量不碰）                               │
│    requestTranslationStart → triggerTranslation →            │
│    runTranslationWorkflow → translateTexts → Google/LLM API  │
│    佇列：MAX_CONCURRENT_TRANSLATIONS = 5，LLM 全域序列化      │
└─────────────────────────────────────────────────────────────┘
```

**為什麼這樣切最安全**：
- 一份「1 檔 × 8 語言」的 Job，被 Expander 展開成 8 筆工作項，丟進**現有佇列**，
  自然地 2 個並行、LLM 序列化執行。**佇列、限流、重試、快取、四種檔案支線全部零修改。**
- 排程器對「怎麼翻譯」一無所知（就像 `translate.js` 對 Google Workspace 一無所知）。
  它只知道「哪些檔案、翻成哪些語言、放哪裡、什麼時候丟進佇列」。

## 四、資料模型（全部是新的、命名空間隔離的 storage key）

> **鐵律：只新增 `schedule*` / `job*` 前綴的 key，絕不改動或重用既有 key。**
> 這樣既有設定、歷史、快取完全不受影響（呼應 [02 §四](02-影響範圍地圖.md)）。

### 4.1 新增 storage key

| Key | 型別 | 說明 |
|---|---|---|
| `scheduleJobs` | `Job[]` | 使用者定義的所有排程任務 |
| `scheduleRuns` | `Run[]` | 執行歷史（每次觸發一筆，含每個工作項的結果，上限例如 50） |
| `scheduleJobCursor_{jobId}` | object | 續傳游標：`{lastModifiedSeen, doneItemKeys[]}`，供增量與斷點續跑 |

### 4.2 Job 結構（一筆排程任務）

```jsonc
{
  "id": "job_abc123",
  "name": "工廠 SOP 多語版",
  "enabled": true,
  "source": {
    "type": "drive-folder",          // ← 見 §5 SOURCE_TYPES 註冊表
    "folderId": "1AbC...",
    "recursive": false,
    "fileTypes": ["presentation", "document"]  // 空 = 全部支援的型態
  },
  "targets": ["es", "vi", "th", "zh-CN"],       // 扇出的語言（來自 i18n 註冊表）
  "destination": {
    "strategy": "per-language-subfolder",       // ← 見 §5 DESTINATION_STRATEGIES
    "rootFolderId": "1XyZ..."                    // 統一目的地根資料夾
  },
  "naming": {
    "template": "[{targetEndonym}] {sourceName}" // ← 見 §5 NAMING tokens
  },
  "schedule": {
    "type": "once-now",                          // ← 見 §5 SCHEDULE_TYPES
    "at": null, "every": null
  },
  "engineProfile": "inherit",     // "inherit" = 用目前的全域引擎設定；或指定一組
  "onlyChanged": false            // 週期重跑時是否只翻改過的檔
}
```

> `engineProfile: "inherit"` 讓排程**不複製一份引擎設定**（避免 API Key 散落多處）。
> 需要「不同 Job 用不同引擎」時再擴充成具名 profile，但預設沿用既有全域設定。

### 4.3 Run 結構（一次執行的結果）

```jsonc
{
  "id": "run_...", "jobId": "job_abc123",
  "startedAt": 0, "finishedAt": 0,
  "status": "running|done|partial|failed|cancelled",
  "items": [
    { "sourceId": "...", "sourceName": "SOP-01",
      "target": "vi", "status": "done",
      "copyId": "...", "url": "https://...", "error": null }
    // 1 檔 × 1 語言 = 1 項
  ]
}
```

## 五、四張擴充註冊表（本設計的靈魂——未來只改資料，不改邏輯）

沿用 [06 §10](06-多語系介面設計.md) 的範式：把「可變的策略」做成資料驅動的註冊表，
每個項目 = `{ id, 標籤, 一個純函式 }`。新增策略 = 加一筆，**不動 runner**。

放在新檔 `scheduler/registry.js`。

### 5.1 `SOURCE_TYPES` — 怎麼蒐集來源檔案

| id | 說明 | 解析函式回傳 |
|---|---|---|
| `active-tab` | 目前分頁的檔案（等同現況，供「立即翻譯本檔成多語」用） | `[{id, name, type}]` |
| `file-list` | 使用者貼上的多個檔案 URL/ID | 同上 |
| `drive-folder` | 一個 Drive 資料夾內所有支援型態的檔案（可選遞迴） | 同上 |
| `drive-folder-changed` | 同上，但只回傳 `modifiedTime > cursor` 的檔（增量） | 同上 |

```js
// 契約：每個來源型態就是一個 async 解析器
// resolve(sourceConfig, ctx) => Promise<Array<{id, name, type}>>
export const SOURCE_TYPES = {
  'drive-folder': {
    label: 'Drive 資料夾',
    resolve: async (cfg, ctx) => ctx.drive.listTranslatable(cfg.folderId, cfg),
  },
  // 新增一種來源（例如 "shared-drive"、"starred"）→ 這裡加一筆即可
};
```

> Drive 清單用 `files.list?q="'{folderId}' in parents and trashed=false"`，
> 依 mimeType 過濾四種支援型態。**已經有 `drive` scope，這是 🟢 純新增的 API 呼叫。**

### 5.2 `DESTINATION_STRATEGIES` — 譯本放哪裡

| id | 行為 | 需要的參數 |
|---|---|---|
| `same-folder` | 放在原檔同資料夾（＝現況） | 無 |
| `unified-folder` | 全部放進一個指定資料夾 | `rootFolderId` |
| `per-language-subfolder` | `{root}/{語言}/…`，每個語言一個子夾（自動建立） | `rootFolderId` |
| `mirror-tree` | 在目的地複製來源的資料夾結構 | `rootFolderId` |

```js
// 契約：resolveParent(item, target, cfg, ctx) => Promise<destParentFolderId>
```

> 這是**唯一需要碰到既有 🔴 函式的地方**：`duplicateGoogleFile()`
> 目前把複本複製到「原檔的 parents」（[background.js](../background.js) 的 `copyId = await duplicateGoogleFile(...)`）。
> 要支援統一目的地，得讓它接受一個**可選** `destParentId`。
> **做法必須是「加參數、給預設值」**：
> ```js
> // 之前：duplicateGoogleFile(fileId, name, mimeType, token)
> // 之後：duplicateGoogleFile(fileId, name, mimeType, token, destParentId = null)
> //       destParentId 為 null 時 → 維持現況（複製到原資料夾），既有行為零改變
> ```
> 這是 🟡 接點（動到共用函式），但**加參數＋預設值**保證現有四種檔案的手動翻譯不受影響。
> 需要 Level 3 測試驗證「不傳 destParentId 時行為完全一致」。

### 5.3 命名模板 token

| token | 展開成 |
|---|---|
| `{sourceName}` | 原檔名 |
| `{targetEndonym}` | 目標語言原生名（繁體中文／Tiếng Việt…，取自 i18n 註冊表） |
| `{targetEnglish}` | 目標語言英文名 |
| `{targetCode}` | 語言代碼（vi、zh-CN…） |
| `{date}` | 執行日期 |

預設 `[{targetEndonym}] {sourceName}` → `[Tiếng Việt] SOP-01`。
新增 token = 在一個 `NAMING_TOKENS` map 加一筆純函式，不動命名引擎。

### 5.4 `SCHEDULE_TYPES` — 什麼時候跑

| id | 說明 | 觸發機制 | 能力階段 |
|---|---|---|---|
| `once-now` | 立即執行一次 | 直接派工 | Phase 1 |
| `once-at` | 指定時間執行一次（限瀏覽器開著） | `chrome.alarms`（單次） | Phase 2 |
| `recurring` | 每日／每週／自訂間隔 | `chrome.alarms`（週期） | Phase 2（在場）／Phase 3（無人值守，需 OAuth 升級） |
| `on-source-change` | 偵測到來源資料夾有新/改檔就跑 | 週期 alarm 輪詢 `modifiedTime` | Phase 3 |

```js
// 契約：每個排程型態負責「算出下一次該在什麼時候被喚醒」
// nextFireTime(scheduleCfg, now) => epochMs | null
```

> **所有排程型態共用同一個 `chrome.alarms` 監聽器**：alarm 響 → 找出到期的 Job → 派工。
> 新增排程型態 = 加一個 `nextFireTime` 函式，**不動 alarm 監聽器本身**。

### 6.3 Job Builder（新增/編輯）：五步精靈

用**單一縱向表單**（不是強制分頁精靈），由上而下五段，每段對應一張註冊表：

1. **來源**：下拉「來源型態」（active-tab / 檔案清單 / Drive 資料夾）
   → 選了 Drive 資料夾就出現 Drive 選取器（見 6.4）。
2. **目標語言**：多選晶片（chips），來源就是 i18n 的 `TARGET_LANGUAGES` 註冊表
   → **與介面語系共用同一份語言清單，不重複維護**。
3. **目的地**：下拉「目的地策略」→ 需要根資料夾的策略就出現資料夾選取器。
4. **命名**：模板輸入框 + 即時預覽（`[Tiếng Việt] SOP-01`）。
5. **排程**：下拉「排程型態」→ once-now 不需其他欄位；once-at 出現時間選擇；
   recurring 出現頻率選擇。**若選的時間 UI 判斷「需瀏覽器開著/需重新授權」，此處即時顯示提示（呼應 C2）。**

> 每一段的「選項」都來自註冊表，所以未來設計師加一個來源型態，UI 下拉**自動多一個選項**，
> 不用改表單程式（就像新增語言時下拉自動出現，見 [06 §10.7](06-多語系介面設計.md)）。

### 6.4 資料夾選取器

Google 沒有可直接嵌入擴充功能的免費資料夾選取器元件（Google Picker API 需額外設定與計費考量）。
**Phase 1 最簡做法**：使用者貼上資料夾的 Drive 網址，我們用正則抽出 folderId
（`drive.google.com/drive/folders/{id}`）並呼叫一次 `files.get` 顯示資料夾名稱確認。
Phase 2+ 再評估是否導入 Google Picker。

### 6.5 執行中的呈現

排程執行時，Job 卡片顯示彙總進度（`7 / 12 完成`），點開看每個「檔案×語言」項的狀態。
**不佔用主面板**——使用者仍可正常手動翻譯當前分頁的檔案（兩者共用同一個佇列，排隊而已）。

### 6.6 i18n

排程面板所有字串一律走既有 i18n（`data-i18n` + `t()`），
新增鍵放在 `schedule.*` 命名空間。**10 個語系都要補這批鍵**（沿用 [06 §10.4](06-多語系介面設計.md) 契約）。

## 七、Job 生命週期與狀態機

```
draft ──儲存──► scheduled ──alarm/立即──► running ──┬─ 全部成功 ─► done
                    ▲                              ├─ 部分失敗 ─► partial ──重試失敗項──► running
                    │                              ├─ 全失敗   ─► failed
                    └──────── recurring 重新排下一次 ◄─┘
                                                   └─ 使用者停止 ─► cancelled
```

- **續傳**：`running` 時 SW 被殺 → 下次 SW 啟動時，排程器檢查有沒有「標記為 running 但已無 active 任務」的 Run，
  依 `scheduleJobCursor` 的 `doneItemKeys` 跳過已完成項，把剩下的重新派工。
- **取消**：重用既有的 `cancelledTasks` 機制——把該 Run 展開出的所有工作項 ID 一次加入取消清單。
- **部分失敗**：例如 12 項中 2 項因 429 最終失敗 → Run 標為 `partial`，UI 提供「只重試失敗的 2 項」。

## 九、分期實作計畫

| Phase | 內容 | 能力 | 需要的前置 | 交付價值 |
|---|---|---|---|---|
| **P1** | 批次扇出 + 統一歸檔，**只有 `once-now`** | 選來源(檔案清單/資料夾) → 多語言 → 歸檔 → 立即執行 | 加 `destParentId`、headless 旁路、Drive 列檔 | **已滿足 E1/E3/E4/P1–P3 的核心**（「一份 SOP 一次翻 8 種語言並歸檔」） |
| **P2** | 加 `once-at` / `recurring`（**限瀏覽器開著**）+ Job 管理 UI | 定時、週期（在場） | `chrome.alarms`、續傳、manifest `alarms` 權限 | 離峰批次、每週重跑 |
| **P3** | 無人值守週期 + `on-source-change` 觸發 + 增量 | 真正的「設定後不用管」 | **OAuth 升級（🔴 前置）**、資料夾輪詢 | E2/E5 的自動化 |

> **建議先只做 P1。** 它不碰 OAuth、不碰 alarms 權限（可先不加，等 P2 再加），
> 風險最低，卻已交付使用者最想要的「一次翻多語 + 自動歸檔」。P2/P3 視回饋再上。

## 十、給未來設計師的「不可退化」清單

1. **不要**把翻譯邏輯寫進排程模組——排程只負責「產生工作項並丟進既有佇列」。
2. **不要**為排程複製一份語言清單——目標語言一律取自 `i18n/languages.js` 的 `TARGET_LANGUAGES`。
3. **不要**新增或重用既有 storage key——排程資料一律 `schedule*`/`job*` 前綴。
4. **不要**讓 `duplicateGoogleFile()` 的新參數變成必填——永遠給預設值以保住手動翻譯。
5. 新增「來源型態／目的地策略／命名 token／排程型態」時，**只在對應註冊表加一筆資料 + 一個純函式**；
   如果你發現得改 `scheduler.js` 的派工迴圈或 alarm 監聽器，八成是設計退化了，停下來重想。
6. 任何「時間 vs OAuth 有效期」的落差，UI 一定要誠實提示，不能讓使用者以為會跑、結果沒跑。

## 十一、待你拍板的關鍵決策

1. **範圍**：先只做 **P1（批次扇出＋歸檔，立即執行）**，還是一路規劃到 P2 排程？
   （建議 P1 先落地。）
2. **無人值守**：你要不要「瀏覽器關著也能半夜自動翻」？
   要 → 必須先立項做 **OAuth 升級**（P3 前置，成本較高）；
   不要 → P1/P2「在場即可」就能覆蓋絕大多數場景，成本低很多。
3. **資料夾選取**：Phase 1 先用「貼 Drive 資料夾網址」的最簡做法可以嗎？
   還是一開始就要 Google Picker 的原生選取體驗（成本較高）？
4. **目的地預設**：預設用 `per-language-subfolder`（{根}/{語言}/…）當推薦值可以嗎？
