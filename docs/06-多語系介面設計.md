## 一、需求範圍

### 要支援的 10 種語系（與目標語言清單一致）

| # | 代碼 | 原生名稱 | 英文名 | 相對英文的長度變化 |
|---|---|---|---|---|
| 1 | `zh-TW` | 繁體中文 | Traditional Chinese | −30%（更短） |
| 2 | `zh-CN` | 简体中文 | Simplified Chinese | −30% |
| 3 | `en` | English | English | 基準 |
| 4 | `ja` | 日本語 | Japanese | −10% |
| 5 | `ko` | 한국어 | Korean | −15% |
| 6 | `es` | Español | Spanish | **+20 ~ 25%** |
| 7 | `fr` | Français | French | **+15 ~ 25%** |
| 8 | `de` | Deutsch | German | **+30 ~ 40%（最長）** |
| 9 | `vi` | Tiếng Việt | Vietnamese | **+20 ~ 30%** |
| 10 | `th` | ไทย | Thai | 長度相近，但**字高更高**（上下附加符號） |

### 納入範圍

- 側邊欄全部介面（主面板、設定、歷史、警告、進度、錯誤訊息、彈窗）
- 說明／教學頁（onboarding.html）
- Chrome Web Store 商店頁的擴充功能名稱與描述

### 不納入範圍（刻意排除，可省下大量工作）

| 項目 | 為什麼排除 |
|---|---|
| **Debug Console 日誌**（`logDebug()` 約 50 條訊息） | 開發者導向，英文才好搜尋與回報問題。保持英文 |
| **RTL（從右至左）版面** | 這 10 種語言**沒有任何一種是 RTL**（沒有阿拉伯文／希伯來文），完全不需要 `dir="rtl"` 的工作。這是很大的範圍縮減 |

| **Google／LLM API 回傳的錯誤原文** | 由對方伺服器決定語言，我們無法控制。只翻譯我們自己包裝的說明文字 |

## 二、關鍵技術決策：**不能**使用 `chrome.i18n`

這是整份設計最重要的一個發現，會決定架構走向。

Chrome 擴充功能的標準 i18n 機制是 `_locales/` 目錄 + `chrome.i18n.getMessage()`。
但它**無法滿足本需求**：

> `chrome.i18n.getMessage()` 的語言由**瀏覽器本身的 UI 語言**決定
> （`chrome://settings/languages`），**Chrome 沒有提供任何 API 讓擴充功能在執行期覆寫它**。

換句話說，用 `chrome.i18n` 的話：
- 使用者只能透過「改整個 Chrome 的語言並重開瀏覽器」來換介面語言
- 擴充功能內的下拉選單**做不出來**

### 結論：採雙軌制

| 用途 | 機制 | 原因 |
|---|---|---|
| **側邊欄與說明頁的介面文字** | **自製執行期 i18n**（本文設計的主體） | 唯一能做到「App 內即時切換」 |
| **manifest 的 `name` / `description`**（商店頁顯示） | **`_locales/` + `chrome.i18n`** | 這是自製方案**碰不到**的地方 —— 商店頁與擴充功能管理頁的文字由 Chrome 讀 manifest 產生，只認 `_locales` |

> ⚠️ **`_locales` 的地雷**：目錄名用**底線**而非連字號，且大小寫有規定 ——
> 是 `_locales/zh_TW/`，**不是** `zh-TW`。同時 manifest 必須加 `"default_locale": "en"`，
> 一旦加了 `default_locale`，Chrome 就會要求 `name`/`description` 改成 `__MSG_xxx__` 形式。

## 三、架構設計

### 3.1 檔案結構

```
i18n/
  languages.js          ← 10 種語言的單一資料來源（見 3.5，順便解決既有地雷 #1）
  i18n.js               ← 載入器：loadLocale() / t() / applyI18n()
  locales/
    en.json             ← 基準語系（也是 fallback）
    zh-TW.json
    zh-CN.json
    ja.json
    ko.json
    es.json
    fr.json
    de.json
    vi.json
    th.json

_locales/               ← 只放 manifest 用的 name/description（各 2 個鍵）
  en/messages.json
  zh_TW/messages.json
  ... （其餘 8 個）
```

**為什麼是「每語系一個 JSON + 執行期 fetch」而不是「全部塞進一個 JS 檔」**：

1. 記憶體裡只留當前語系（10 × 約 130 個鍵全載入是浪費）
2. 翻譯人員編輯純 JSON，不會誤改程式碼
3. **不需要 build step** —— 符合本專案「零依賴、無編譯」的既有哲學
4. `fetch(chrome.runtime.getURL('i18n/locales/ja.json'))` 在側邊欄與 Service Worker 都能用

### 3.3 HTML 標記方式

在既有 HTML 上加屬性，**英文原文留在標籤內**當作預設值：

```html
<!-- 純文字 -->
<h3 data-i18n="settings.title">Extension Settings</h3>

<!-- placeholder -->
<input id="api-key" data-i18n-placeholder="settings.apiKey.placeholder" placeholder="Enter API Key">

<!-- tooltip -->
<button id="btn-help" data-i18n-title="header.help" title="Setup Guide">

<!-- 含 <strong> / <br> 等標記的段落 -->
<p data-i18n-html="settings.quotaTip">For best results, choose a model with <strong>…</strong></p>
```

**保留英文原文在 HTML 裡有兩個好處**：
1. i18n 載入失敗時畫面仍是可讀的英文，不會變空白
2. 英文原文本身就是翻譯的 source of truth，翻譯人員可直接對照

### 3.4 核心 API

```js
// i18n/i18n.js
let messages = {};      // 當前語系
let fallback = {};      // 永遠是 en

export async function loadLocale(code) {
  if (!fallback.__loaded) fallback = await fetchLocale('en');
  messages = code === 'en' ? fallback : await fetchLocale(code);
  document.documentElement.lang = code;      // 讓瀏覽器套用正確的斷行與字型規則
}

// t('progress.duplicating', { fileType: 'presentation' })
export function t(key, params) {
  let s = messages[key] ?? fallback[key] ?? key;   // 三層 fallback，永不回傳空字串
  if (params) {
    for (const [k, v] of Object.entries(params)) {
      s = s.replaceAll(`{${k}}`, v);
    }
  }
  return s;
}

export function applyI18n(root = document) {
  root.querySelectorAll('[data-i18n]').forEach(el =>
    el.textContent = t(el.dataset.i18n));
  root.querySelectorAll('[data-i18n-placeholder]').forEach(el =>
    el.placeholder = t(el.dataset.i18nPlaceholder));
  root.querySelectorAll('[data-i18n-title]').forEach(el =>
    el.title = t(el.dataset.i18nTitle));
  root.querySelectorAll('[data-i18n-html]').forEach(el =>
    el.innerHTML = t(el.dataset.i18nHtml));   // 僅用於我們自己撰寫的字串
}
```

**三層 fallback（當前語系 → 英文 → 鍵名本身）是刻意設計**：
翻譯漏了一個鍵時，畫面會顯示 `settings.title` 這種鍵名 ——
**醜但立刻看得見**，遠勝於顯示空白讓人找不到原因。

> ⚠️ `data-i18n-html` 用 `innerHTML`，**只能餵我們自己寫在 JSON 裡的字串**，
> 絕不可餵 API 回傳的內容（那是 [05-已知問題 L3](05-已知問題與技術債.md) 的 XSS 風險）。

### 3.5 難題 A：語言清單的單一資料來源（順便解決既有地雷 #1）

目前語言清單已經被複製在**三個地方**（[02-影響範圍地圖 地雷 #1](02-影響範圍地圖.md)）。
加上介面語言選單就會變成**四個地方** —— 所以這次一定要先收攏。

```js
// i18n/languages.js —— 唯一資料來源
export const LANGUAGES = [
  { code: 'zh-TW', endonym: '繁體中文',  english: 'Traditional Chinese' },
  { code: 'zh-CN', endonym: '简体中文',  english: 'Simplified Chinese' },
  { code: 'en',    endonym: 'English',   english: 'English' },
  { code: 'ja',    endonym: '日本語',     english: 'Japanese' },
  { code: 'ko',    endonym: '한국어',     english: 'Korean' },
  { code: 'es',    endonym: 'Español',   english: 'Spanish' },
  { code: 'fr',    endonym: 'Français',  english: 'French' },
  { code: 'de',    endonym: 'Deutsch',   english: 'German' },
  { code: 'vi',    endonym: 'Tiếng Việt', english: 'Vietnamese' },
  { code: 'th',    endonym: 'ไทย',       english: 'Thai' },
];
```

四個消費端從此都讀它：

| 消費端 | 用哪個欄位 | 目前的重複位置 |
|---|---|---|
| 目標語言 `<select>` | `english (endonym)` | popup.html:74-83（硬寫 10 個 option） |
| **介面語言 `<select>`（新增）** | **`endonym` 單獨顯示** | — |
| LLM prompt 的語言名 | `english` | translate.js:2 `LANG_NAMES` |
| 譯本檔名 `[Translated - X]` | `endonym` | background.js:331 `LANG_LABELS` |

兩個 `<select>` 都改由 JS 依 `LANGUAGES` 動態產生。
**這是本功能最大的附加價值**：地雷 #1 從此消失。

> **關鍵 UX 規則**：介面語言選單**只顯示 endonym**（`日本語`、`Deutsch`），
> 且**永遠不隨當前語系改變**。理由：使用者誤選成看不懂的語言時，
> 必須還能靠原生名稱找回自己的語言。這是所有主流軟體的做法。

### 3.6 難題 B：Service Worker 產生的進度訊息

**這是本設計最棘手的技術問題。**

我盤點到 background.js 有 **16 處 `sendProgress()` + 4 處佇列狀態**，
共約 20 條**使用者可見**的字串是在 Service Worker 裡組出來的：

```js
// background.js:328 目前寫法
sendProgress('copy', 25, `Duplicating ${fileTypeName} on Google Drive...`);
// background.js:1623
status: `Waiting in queue (Position: #${queuePos})...`
```

Service Worker 不該知道使用者選了什麼介面語言（那是 UI 層的偏好），
而且這些字串會被**持久化**到 `taskState_{fileId}`。

**解法：背景只送「鍵 + 參數」，翻譯留在 UI 層做。**

```js
// background.js 改成
sendProgress('copy', 25, { key: 'progress.duplicating', params: { fileType: fileTypeName } });
```

```js
// popup.js handleProgress() 改成
progressStatus.textContent =
  typeof status === 'string' ? status : t(status.key, status.params);
```

**這個 `typeof` 判斷同時解決了向後相容**：
`chrome.storage.local` 裡既有的 `taskState_` 是舊格式（純字串），
升級後仍能正常顯示，**不需要寫資料遷移程式**。

附帶要處理的兩件事：
- `fileTypeName`（`presentation`/`document`/`spreadsheet`/`form`）本身要變成鍵
  （`fileType.presentation`），由 UI 端翻譯後再代入
- 引擎名稱（`GEMINI`、`OPENAI`）是**專有名詞，不翻譯**

### 3.7 難題 C：帶參數與複數

需要參數代換的字串不多，用最簡單的 `{name}` 佔位即可（見 3.4 的 `t()`）。

**複數則刻意不做**：只有 `Translating N texts` 與 `Position #N` 兩處會碰到。
10 種語言的複數規則差異很大（俄文有 3 種、阿拉伯文有 6 種），
要正確處理得引入 ICU MessageFormat 引擎 —— 對兩個字串來說完全不划算。

**建議改寫句型迴避複數**，例如
`Translating N texts…` → `Translating… ({count} items)`，
中文、日文、韓文、泰文本來就沒有複數變化，歐語系用括號數量的寫法也完全自然。

## 四、執行流程

### 4.1 啟動（每次開側邊欄）

```
1. popup.js DOMContentLoaded
2. 讀 chrome.storage.local 的 uiLang
   ├─ 有值 → 用它
   └─ 無值（首次安裝）→ 自動偵測：
        chrome.i18n.getUILanguage()  例如 'zh-TW' / 'ja-JP' / 'de'
        ├─ 完全符合 LANGUAGES → 用它
        ├─ 只有主語言碼相符（'ja-JP' → 'ja'）→ 用主語言碼
        └─ 都不符 → 'en'
3. await loadLocale(uiLang)
4. applyI18n()                    ← 必須在其他 UI 初始化「之前」
5. 動態產生兩個語言 <select> 的 options
6. 其餘既有初始化流程
```

> 首次安裝自動偵測瀏覽器語言是重要的第一印象 —— 台灣使用者裝好就是中文介面，
> 不需要先去設定裡找。但**偵測結果要寫進 `uiLang`**，之後就以使用者選擇為準。

### 4.2 使用者切換語言

```
1. <select id="select-ui-lang"> change 事件
2. chrome.storage.local.set({ uiLang })
3. await loadLocale(uiLang)
4. applyI18n()                    ← 立即重繪，不需要重開面板
5. 重新套用「JS 動態產生」的文字：
   - 狀態徽章 updateStatusBadge(目前狀態)
   - 目前的進度訊息（若翻譯進行中）
   - 歷史清單 renderHistoryList()
   - 檔案類型標籤 metaLabel
```

**第 5 步是最容易漏的地方**：`applyI18n()` 只處理有 `data-i18n` 屬性的元素，
而 popup.js 裡約 40 處是用 `textContent =` 直接寫入的動態文字。
切換語言後**必須重新呼叫產生這些文字的函式**，否則會出現「一半新語言、一半舊語言」。

**建議做法**：把這些動態重繪集中成一個 `refreshDynamicTexts()`，
語言切換與初始化都呼叫它，避免日後漏掉。

### 4.3 說明頁（onboarding.html）

同樣機制，但它是獨立分頁：載入時讀 `uiLang` → `loadLocale()` → `applyI18n()`。
**不需要**自己的語言選單（跟隨側邊欄的設定即可）。

**為什麼放設定裡而不是標題列**：

再加一個地球圖示會過度擁擠。語言是**偏好設定**而非動作，歸屬設定面板語意正確。

### 重要行為決策：**立即生效，不受 Save/Cancel 管轄**

介面語言一選就立刻切換並寫入 storage，**不需要按 Save**。

理由：使用者需要**立刻看到結果**來確認自己選對了語言。
若要求按 Save 才生效，選錯語言的人會困惑。

但這與同面板其他欄位（要按 Save）的行為不一致，所以：
- 在該卡片加一行小字說明「Applies immediately」
- **這張卡片必須放在自己的 card 裡**，視覺上與受 Save 管轄的區塊分開

> 順帶提醒：這與 [05-已知問題 M5](05-已知問題與技術債.md)（Test Connection 後按 Cancel
> 造成狀態不一致）是同一類問題。實作時建議一起處理，把「立即生效」與
> 「需按 Save」的欄位在視覺上明確分開。

## 六、排版風險（真正的 bug 會從這裡來）

側邊欄只有 320–380px 寬。**德文平均比英文長 30–40%**，這是最大風險。

### 已知的緊繃處

| 位置 | 英文 | 德文（估） | 風險 |
|---|---|---|---|
| 儲存按鈕 | `Save Configurations` (19) | `Konfigurationen speichern` (26) | 🔴 `.settings-actions` 是 `grid-template-columns: 1fr 1.5fr`，可能溢出 |
| 主按鈕 | `Translate & Copy` (16) | `Übersetzen & kopieren` (21) | 🟡 |
| 測試按鈕 | `Test Connection` (15) | `Verbindung testen` (17) | 🟡 與狀態徽章同一列，兩者一起變長 |
| 狀態徽章 | `Unverified` (10) | `Nicht verifiziert` (17) | 🟡 同上 |
| 四顆步驟燈 | `Duplicate original document` (27) | 約 38 字元 | 🟡 需容許換行 |
| 目標語言標籤 | `Translate Target Language` (25) | 約 33 字元 | 🟢 獨立一行，空間足夠 |

### 對策

1. **不要在會被翻譯的文字上用 `white-space: nowrap`**
   （目前 `.brand-name` 有用，但那是產品名不翻譯，可以留）
2. **按鈕允許換兩行**，或在窄寬度下略縮字級
3. **`.settings-actions` 的 grid 比例改成 `1fr 1.6fr` 或改用 flex + `min-width: 0`**
4. **泰文**：`line-height` 從 1.4 提高到約 1.6（上下附加符號會被裁切），
   且**不要**對泰文段落用 `word-break: break-all`
   （目前只有 log console 在用，那是 ASCII 等寬字，沒問題）
5. **驗收基準**：在 **320px 寬 + 德文**下逐頁檢查，這是最壞情況

### 字型注意事項

目前字型堆疊是：
```css
font-family: 'Outfit', -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif;
```

`Outfit` **只含拉丁字元**，所以中日韓文與泰文會 fallback 到系統字型
（現況已經是這樣，中文本來就是系統字型渲染的）。

建議明確補上 CJK 與泰文的 fallback，避免不同平台落差：
```css
font-family: 'Outfit', -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto,
             "Noto Sans TC", "Noto Sans SC", "Noto Sans JP", "Noto Sans KR",
             "Noto Sans Thai", "PingFang TC", "Microsoft JhengHei", sans-serif;
```

> 另外注意：popup.html 目前從 `fonts.googleapis.com` **遠端載入**字型。
> 這在擴充功能裡是隱私與離線可用性的隱憂（每次開面板都對 Google 發請求）。
> 與 i18n 無直接關係，但既然要改字型堆疊，建議一併評估改為內嵌字型檔。

### 9.1 偽本地化（pseudo-localization）—— 性價比最高的一招

## 十、擴充性規範：未來如何快速新增語系

> **這是本設計的核心目標之一。**
> 設計準則：**新增一個介面語系，只需要「1 筆註冊資料 + 1 個 JSON 檔 + 跑 1 個檢查腳本」，
> 不需要改動任何一行邏輯程式碼。**
>
> 若你發現新增語系時必須修改 popup.js / background.js / popup.css，
> 那就是設計沒做到位，應該回頭把該處改成由註冊表驅動。

### 10.1 語言註冊表（唯一的擴充點）

3.5 節的 `LANGUAGES` 要設計成**完整自我描述**的註冊表 ——
把「這個語言有什麼特性」全部宣告在資料裡，讓程式碼只讀資料、不寫條件判斷：

```js
// i18n/languages.js —— 新增語系時「唯一」需要動的檔案
export const LANGUAGES = [
  {
    code:      'en',            // BCP 47 語言標籤，同時是 locales/<code>.json 的檔名
    endonym:   'English',       // 原生名稱（語言選單顯示用，永不翻譯）
    english:   'English',       // 英文名稱（LLM prompt 用）
    dir:       'ltr',           // 'ltr' | 'rtl'
    fallback:  null,            // 缺鍵時往哪個語系找；en 是根，故為 null
    ui:        true,            // 是否可作為「介面語言」
    target:    true,            // 是否可作為「翻譯目標語言」
    lineHeight: 1.4,            // 基礎行高（排版微調）
    fontStack: 'latin',         // 對應 popup.css 的字型堆疊變數
  },
  {
    code: 'zh-TW', endonym: '繁體中文', english: 'Traditional Chinese',
    dir: 'ltr', fallback: 'en', ui: true, target: true,
    lineHeight: 1.5, fontStack: 'cjk-tc',
  },
  {
    code: 'th', endonym: 'ไทย', english: 'Thai',
    dir: 'ltr', fallback: 'en', ui: true, target: true,
    lineHeight: 1.65,           // ← 泰文上下附加符號需要更高行高，宣告在這裡而非散落在 CSS
    fontStack: 'thai',
  },
  // ... 其餘 7 個語系
];
```

### 10.2 每個欄位為什麼存在（都是為了「將來不用改程式」）

| 欄位 | 解決什麼未來問題 |
|---|---|
| `code` | 同時當 JSON 檔名，所以載入器不需要任何對照表 |
| `endonym` | 語言選單標籤。**新增語系時選單自動長出新選項**，不必改 HTML |
| `english` | LLM prompt 的語言名。取代 translate.js 的 `LANG_NAMES` |
| **`dir`** | **RTL 預備**。目前 10 種語言都是 `ltr`，但將來若要加**阿拉伯文／希伯來文**，只要填 `dir: 'rtl'`，載入器會自動設 `document.documentElement.dir`。**架構不用重做，只需補一次 CSS 邏輯屬性的掃描** |
| **`fallback`** | **區域變體預備**。將來要加港式中文 `zh-HK`，只需 `fallback: 'zh-TW'` —— 只翻譯有差異的鍵，其餘自動沿用繁中，不必整份重譯 |
| **`ui` / `target`** | **兩份清單解耦**。介面語系與翻譯目標語系將來可能不同步（例如想支援阿拉伯文介面，但翻譯目標暫不開放；或反之）。有了旗標就不必拆成兩個陣列 |
| `lineHeight` / `fontStack` | **排版差異宣告化**。泰文行高、CJK 字型這類需求集中在註冊表，不會散落在 CSS 各處變成找不到的魔術數字 |

### 10.3 排版差異由註冊表驅動（不要寫死在 CSS）

載入語系時，把註冊表的排版設定寫成 CSS 變數：

```js
// i18n/i18n.js loadLocale() 內
const lang = LANGUAGES.find(l => l.code === code);
const root = document.documentElement;
root.lang = code;                       // 讓瀏覽器套用正確斷行/連字規則
root.dir  = lang.dir;                   // RTL 預備
root.dataset.fontStack = lang.fontStack;
root.style.setProperty('--i18n-line-height', lang.lineHeight);
```

CSS 端只讀變數與 data 屬性，**永遠不需要為新語言加規則**：

```css
:root {
  --i18n-line-height: 1.4;
  --font-latin: 'Outfit', -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif;
  --font-cjk-tc: 'Outfit', "Noto Sans TC", "PingFang TC", "Microsoft JhengHei", sans-serif;
  --font-cjk-sc: 'Outfit', "Noto Sans SC", "PingFang SC", "Microsoft YaHei", sans-serif;
  --font-jp:     'Outfit', "Noto Sans JP", "Hiragino Sans", "Yu Gothic", sans-serif;
  --font-kr:     'Outfit', "Noto Sans KR", "Apple SD Gothic Neo", "Malgun Gothic", sans-serif;
  --font-thai:   'Outfit', "Noto Sans Thai", "Thonburi", sans-serif;
}

body { line-height: var(--i18n-line-height); font-family: var(--font-latin); }

html[data-font-stack="cjk-tc"] body { font-family: var(--font-cjk-tc); }
html[data-font-stack="cjk-sc"] body { font-family: var(--font-cjk-sc); }
html[data-font-stack="jp"]     body { font-family: var(--font-jp); }
html[data-font-stack="kr"]     body { font-family: var(--font-kr); }
html[data-font-stack="thai"]   body { font-family: var(--font-thai); }
```

> 新增語系若沿用既有字型堆疊（例如加西班牙文 → `fontStack: 'latin'`），
> **CSS 完全不用動**。只有引進全新書寫系統（如天城文、阿拉伯文）才需要多加一組變數。

### 10.4 語系檔契約（Locale File Contract）

每個 `i18n/locales/<code>.json` 必須遵守：

```json
{
  "_meta": {
    "code": "zh-TW",
    "name": "繁體中文",
    "basedOnEnVersion": 3,
    "completeness": "full",
    "reviewedBy": "native-speaker",
    "updatedAt": "2026-08-04"
  },

  "header.help": "設定指南",
  "settings.title": "擴充功能設定",
  "progress.duplicating": "正在於 Google Drive 複製{fileType}…"
}
```

**硬規則（違反會被 10.5 的檢查腳本擋下）**：

| 規則 | 說明 |
|---|---|
| **扁平鍵值，禁止嵌套** | 鍵用點號分層（`settings.title`），但 JSON 結構是**一層**。理由：`t()` 不需要遞迴查找，且 diff 好讀 |
| **參數佔位必須完整保留** | `en` 有 `{fileType}`，譯文就必須有 `{fileType}`。**這是最常見的翻譯錯誤** |
| **不得新增 `en.json` 沒有的鍵** | 多出來的鍵代表 `en` 漏了，或是譯者自行加料 |
| **`_meta.basedOnEnVersion`** | 對應 `en.json` 的 `_meta.version`。`en` 改版後版號不符即代表此語系需要更新 |
| **`completeness`** | 涵蓋率：`full`（全譯）/ `partial`（部分，其餘靠 fallback 鏈）。**只描述「有幾個鍵」** |
| **`reviewedBy`** | 品質：`source`（英文原文）/ `native-speaker`（母語者校閱過）/ `machine`（機器翻譯未校閱）。**只描述「品質是否被人驗證」**。與 `completeness` 是兩個獨立維度 —— 一份翻譯可以「全譯但未校閱」 |
| **不得含 HTML `<script>`／事件屬性** | `data-i18n-html` 走 `innerHTML`，只允許 `<strong> <em> <br> <a> <code>` |

`en.json` 是**唯一的 source of truth**，額外帶版號：

```json
{ "_meta": { "code": "en", "version": 3, "keyCount": 130 } }
```

### 10.5 檢查腳本（保證新增語系不會漏東西）

專案沒有 build step，所以提供一支**開發時手動執行、不隨產品打包**的驗證腳本
`i18n/validate.mjs`：

```bash
node i18n/validate.mjs
```

它會檢查：

| 檢查項 | 抓出什麼問題 |
|---|---|
| 註冊表 ↔ 檔案雙向比對 | `LANGUAGES` 有 `de` 但缺 `locales/de.json`（或反之） |
| 對 `en.json` 做鍵完整性比對 | 缺鍵（列出清單）／多餘鍵 |
| **參數佔位一致性** | 譯文漏掉 `{fileType}`、`{count}` —— 執行期才爆的隱性 bug |
| 字串長度比 | 超過英文 150% 的字串（版面溢出高風險），列出來預先檢視 |
| `_meta` 欄位齊備與版號相符 | `basedOnEnVersion` 落後於 `en.json` 的 `version` |
| 危險 HTML | `data-i18n-html` 用的字串含不允許的標籤 |
| 孤兒鍵 | `en.json` 有但程式碼裡沒有任何地方引用（grep `data-i18n` 與 `t('`） |

輸出範例：

```
✔ en     130/130  v3
✔ zh-TW  130/130  v3
✖ de     127/130  v3   缺 3 鍵：settings.status.invalid, history.empty, error.timeout
⚠ de     settings.btnSave 長度為英文的 168%（版面溢出風險）
✖ fr     progress.duplicating 遺漏參數 {fileType}
✔ th     130/130  v3
```

> 這支腳本是「快速新增語系」的關鍵。有它才敢把翻譯外包 ——
> 交回來直接跑一次就知道完不完整，不用人工比對 130 個鍵。

### 10.5b 覆蓋率腳本（保證「還差多少」是數字而不是驚喜）

`validate.mjs` 檢查語系檔**互相之間**是否一致，但它對另一種失敗完全無感：
**根本沒有鍵的硬編碼字串**。所以另外提供：

```bash
node i18n/coverage.mjs            # 依畫面區域列出覆蓋率
node i18n/coverage.mjs --list     # 逐條列出仍硬編碼的字串
node i18n/coverage.mjs --min 95   # 低於門檻則 exit 1（可用於 git hook）
```

它按**使用者實際看到的畫面區域**分別統計（主畫面／設定／歷史／警告／彈窗／說明頁），
因為「整體 57%」會掩蓋「主畫面 0%」這種真正嚴重的狀況。

**設計要點：誤報率必須壓到零。** 初版有 75% 誤報（把 `data-i18n-html`
的子元素、HTML 註解、模型名稱都算成漏抽），一個雜訊這麼高的指標沒人會信，
等於又回到「工具沒人跑」的老問題。現已處理：

- 跳過 `data-i18n` / `data-i18n-html` 元素的**整個子樹**（內容由語系字串提供）
- 跳過 HTML 註解與 `<svg>` 內容
- 跳過技術識別碼（模型名、網址、CSS token）
- 跳過已內含 `t(...)` 的模板字串
- **`data-i18n-ignore` 屬性**：明確標記「這條由 JS 在執行期負責」的例外
  （例如 `steps.copy` 帶 `{fileType}` 參數，`applyI18n()` 無法填）

### 10.6 `_locales/` 由腳本產生，不要手寫

manifest 的商店名稱／描述需要 `_locales/<code>/messages.json`（見第二節），
若手寫就變成「新增語系要改兩處」。改由腳本從註冊表 + 語系檔產生：

```bash
node i18n/build-manifest-locales.mjs     # 打包前執行
```

它讀取每個語系的 `store.appName` 與 `store.appDescription` 兩個鍵，
輸出 `_locales/<底線格式>/messages.json`（自動處理 `zh-TW` → `zh_TW` 的格式轉換 ——
這正是最容易手寫寫錯的地方）。

### 10.7 ✅ 新增一個語系的標準流程（例：新增印尼文）

**只有三步，而且第 4 步是驗證而非工作：**

```
① 在 i18n/languages.js 加一筆：
   {
     code: 'id', endonym: 'Bahasa Indonesia', english: 'Indonesian',
     dir: 'ltr', fallback: 'en', ui: true, target: true,
     lineHeight: 1.4, fontStack: 'latin',
   }

② 複製 i18n/locales/en.json → i18n/locales/id.json，翻譯所有值
   （更新 _meta：code / name / basedOnEnVersion / completeness / reviewedBy / updatedAt）

③ 打包前執行：
   node i18n/build-manifest-locales.mjs

④ 驗證：
   node i18n/validate.mjs          → 必須全綠
   手動：切到印尼文，在 320px 寬檢查版面
```

**不需要改動**：popup.html、popup.js、popup.css、background.js、translate.js、manifest.json

兩個語言下拉選單會自動長出新選項（因為是從 `LANGUAGES` 動態產生），
LLM prompt 的語言名、譯本檔名也都自動生效。

### 10.8 特殊情境的擴充做法

| 情境 | 做法 | 要額外做什麼 |
|---|---|---|
| **加區域變體**（港式中文 `zh-HK`） | `fallback: 'zh-TW'`，`id.json` 只寫**有差異**的鍵 | 無。fallback 鏈自動處理 |
| **只想開放介面、不開放為翻譯目標** | `ui: true, target: false` | 無 |
| **只想開放為翻譯目標、介面暫不支援** | `ui: false, target: true`，**不需要**建 locale 檔 | 無 |
| **先上機器翻譯版試水溫** | `completeness: 'machine'` | 建議 UI 在選單該項後綴顯示 `(Beta)` |
| **加 RTL 語言**（阿拉伯文／希伯來文） | `dir: 'rtl'` | ⚠️ **這是唯一需要改 CSS 的情境**：要把 popup.css 的 `left`/`right`/`margin-left` 等改成邏輯屬性（`inset-inline-start`、`margin-inline-start`）。**建議在 Phase 1 就順手改成邏輯屬性**，將來加 RTL 就變成純資料變更 |
| **加全新書寫系統**（印度語系、緬甸文等） | 在 10.3 的 CSS 新增一組 `--font-xxx` | 只加變數，不改邏輯 |

> 💡 **Phase 1 的額外建議**：把 popup.css 的方向性屬性一次改成 CSS 邏輯屬性。
> 這件事現在做只是機械替換（我們剛把版面改成流動式，時機正好），
> 但等到將來要支援阿拉伯文才做，就得在 1200 行 CSS 裡逐條找。

### 10.9 給維護者的「不可退化」清單

實作完成後，這些規則必須守住，否則擴充性會慢慢腐蝕：

- [ ] **語言選單不得出現硬寫的 `<option>`** —— 一律從 `LANGUAGES` 產生
- [ ] **程式碼不得出現 `if (lang === 'th')` 這種語言特例判斷** —— 差異一律宣告進註冊表
- [ ] **不得在 CSS 寫 `[lang="ja"] { ... }` 這類單一語言規則** —— 走 `--font-*` / `--i18n-line-height` 變數
- [ ] **不得在 JS 裡寫死使用者可見文字** —— 一律走 `t()` 或 `data-i18n`
- [ ] **新增字串必須同時加進 `en.json` 並遞增 `_meta.version`** —— 否則其他語系不知道自己過期了
- [ ] **每次發布前跑 `node i18n/validate.mjs` 與 `node i18n/coverage.mjs`** —— 已寫進 [04-版本與發布](04-版本與發布.md) 的發布檢查表
- [ ] **側邊欄覆蓋率不得低於 100%** —— 新增畫面時同步加 `data-i18n`，
      真的必須由 JS 負責就加 `data-i18n-ignore` 並註明原因

## 十三、Phase 2 完成紀錄（2026-08-04）與一個重要教訓

### 教訓：指標的**分母**錯了，比沒有指標更危險

Phase 1 完成後 `coverage.mjs` 回報「側邊欄 100%」，但使用者實測仍看到英文。原因不是漏標，
而是**這個指標只掃 `popup.html` + `popup.js`**。使用者可見的字串其實來自三個檔案：

| 檔案 | 當時是否納入統計 | 實際含有的使用者可見字串 |
|---|---|---|
| `popup.html` / `popup.js` | ✅ 有 | 已 100% |
| **`background.js`** | ❌ **完全沒掃** | 19 個 `sendProgress` + 3 個佇列字串 |
| **`translate.js`** | ❌ **完全沒掃** | `throw` 出來、會原樣顯示給使用者的錯誤 |

所以「100%」是用**約三分之二的真實範圍**當分母算出來的。

> **規範補充（務必遵守）**：任何新增的、會把文字送到使用者眼前的程式檔，
> **必須同時加進 `coverage.mjs` 的 `JS_TARGETS`**。
> 指標只能證明它掃過的範圍——分母錯了，百分比再漂亮也是假的。

### 第二個教訓：修誤報時製造了漏報

Phase 1 為了消除誤報，在 JS 掃描器加了「字串含 `<svg` 就整條跳過」。
但 `resetProgress()` 的 `'<span>Stop Translation</span><svg…>'` 正好符合，
於是這顆按鈕的英文被工具視而不見。

**現在的做法**：先剝掉 SVG 與標籤，再判斷**剩下的文字**是不是文案。
已用「重新注入 bug」的方式驗證這兩類問題現在都會被抓到並讓 `--min` 門檻 `exit 1`。

### Phase 2 實作內容

**協定變更**：background.js 不再送組好的字串，改送 `{ key, params }`，翻譯留在 UI 層。

```js
// 之前
sendProgress('copy', 25, `Duplicating ${fileTypeName} on Google Drive...`);
// 之後
sendProgress('copy', 25, { key: 'progress.duplicating',
                           params: { fileType: `@fileType.${fileTypeName}` } });
```

**`@key` 慣例**：參數值以 `@` 開頭時，`t()` 會把它當成另一個鍵再解析一次。
這讓 Service Worker 能傳遞「可翻譯的名詞」（如檔案類型）而不必知道當前語言。

**向後相容**：`tStatus()` 同時接受 `{key, params}` 與純字串，
所以舊版寫進 `chrome.storage.local` 的 `taskState_*` 仍能正常顯示，**不需要資料遷移**。

**錯誤訊息分類修正**：我原先把 `Translation mismatch: sent 35 items...` 歸類為
「API 回傳的原文，無法控制」——**這是錯的**，那是 `translate.js` 自己 `throw` 的字串。
現在的設計是：`throw` 保持英文（方便 grep 與回報問題），
由 `translateErrorToHuman()` 依英文標記比對後回傳當地語言的友善說明。
新增 `error.mismatch` 與 `error.invalidFormat` 兩支。
