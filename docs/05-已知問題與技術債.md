## 🔴 高優先（會造成使用者可見的故障）

### ~~H1. Google API 呼叫完全沒有重試與逾時保護~~ ✅ 已於 2026-08-06 修正

> **已修正。** `translate.js` 的 `fetchWithRetryAndTimeout()` 已 `export`，
> `background.js` 新增 `googleApiFetch()` 包裝（`useLock=false`、`cooldownMs=0`、
> 重試 3 次、逾時 60s），並套用到 **11 個**翻譯關鍵路徑的 Google 呼叫：
> 複製（get parents + copy）、Slides/Docs 的 get 與 batchUpdate、Sheets 的 get 與 write、
> Forms 的 get 與 write、以及取消時的 delete。
> 實測：模擬 Drive 回 500 兩次，第三次自動復原成功。
>
> **刻意未包裝**兩處：`syncHistoryFiles`（本身已有「模糊錯誤一律保留」的容錯）、
> 死程式碼 `duplicatePresentation()`（無人呼叫，見 M4）。
>
> ⚠️ **仍有殘留**：`fetchWithRetryAndTimeout` **不重試 401**，所以 [H2](#h2-oauth-token-取得後全程不更新且-401-不會重試)
> 的長任務 token 過期問題**尚未解決**——那需要 token 更新機制，與本次重試無關。
>
> 以下保留原始問題描述作為背景。

**原現象**：LLM 呼叫有完整的重試機制，但**Google API 呼叫一個都沒有**。

驗證：
```bash
grep -c "await fetch(" background.js        # → 13
grep -c "fetchWithRetry" background.js      # → 0
```

`translate.js` 有寫得很好的 `fetchWithRetryAndTimeout()`（重試 429/5xx、指數退避、逾時），
但 background.js 裡 13 個 Google API 呼叫**全部是裸 `fetch()`**：
`duplicateGoogleFile`、`getPresentationDetails`、`updatePresentation`、
`getDocumentDetails`、`updateDocument`、Sheets 的讀寫、Forms 的讀寫、`deleteGoogleFile`。

**後果**：
- Google API 偶發的 500/503（實務上會發生）→ 整個翻譯直接失敗，使用者要從頭重來
- 網路瞬斷 → 同上
- 沒有逾時 → 請求可能無限期掛住，使用者只看到「Taking longer than expected」

**修法**（成本低、效益高）：把 `fetchWithRetryAndTimeout` 從 translate.js `export` 出來，
在 background.js `import` 後替換這 13 個呼叫。注意 `useLock` 要傳 `false`
（Google API 不該和 LLM 共用限流鎖）。

**爆炸半徑**：🔴🔴 動到全部四種檔案類型 → 需要 Level 3 測試。

### ~~H2. OAuth token 取得後全程不更新，且 401 不會重試~~ ✅ 已於 2026-10-25 修正（v1.5.0）

**位置**：[background.js:602](../background.js:602) `getAuthToken()`

用的是 **Implicit Flow**（`response_type=token`），**拿不到 refresh token**。
Google 的 access token 有效期約 1 小時。

流程中 token 只在**開始時取得一次**（[background.js:323](../background.js:323)），
之後一路傳到最後的寫回動作。

**後果**：翻譯一份超大檔案（大量文字 × 4.2 秒冷卻 × 重試）若耗時超過 1 小時，
最後的 `batchUpdate` 會拿到 401。而 `fetchWithRetryAndTimeout` **只重試 429 與 5xx，不重試 401**
（[translate.js:283](../translate.js:283)），加上 H1 的問題，Google API 根本不重試 →
**前面所有翻譯成果全部白費，複本留在 Drive 但沒翻完**。

**修法**（兩種，可並行）：
1. 短期：在寫回前重新呼叫 `getAuthToken()`（靜默模式很快）
2. 長期：改用 Authorization Code Flow + PKCE 取得 refresh token（成本較高）

### ~~H3. Service Worker 被回收會讓進行中的翻譯永久中斷~~ ✅ 已於 2026-10-25 修正（v1.5.0）

**位置**：[background.js:14](../background.js:14) `cleanUpStaleStates()`

Manifest V3 的 Service Worker 沒有常駐保證。目前的對策是側邊欄每 10 秒 ping 一次
（[popup.js:486](../popup.js:486)），但這只在**側邊欄開著**時有效。

**後果**：使用者關掉側邊欄去做別的事 → SW 可能被回收 → 翻譯中斷。
下次 SW 啟動時 `cleanUpStaleStates()` 把任務標記為
「Translation interrupted by browser or extension restart」。

**目前的處理算是誠實的**：不只有明確的中英雙語錯誤訊息告知使用者重試，
翻譯進行中也已經在進度區顯示警告橫幅（[popup.html:109](../popup.html:109)
「翻譯進行中，請勿關閉或切換此文件分頁，以防翻譯中斷。」）。
所以這不算 bug，而是**架構上的固有限制**。

**修法建議**（按成本排序）：
1. 中等：改用 `chrome.alarms` 每 20 秒喚醒 SW（比 ping 可靠，**不依賴側邊欄開著**）
2. 較貴：把工作流程改成可續傳（記錄「已完成到第幾批」，中斷後從該批繼續）

### ~~H4. LLM 回傳含非法跳脫字元會導致整批翻譯失敗~~ ✅ 已於 2026-08-06 修正

**原問題**（使用者實際回報）：翻譯中止，Log 顯示
`Translation workflow failed: SyntaxError: Bad escaped character in JSON at position N`。

**根因**：LLM 回傳的 JSON 字串值裡含**非法跳脫序列**——一個 `\` 後面接的不是
JSON 合法跳脫字元（`" \ / b f n r t` 或 `uXXXX`）。常見來源：譯文含 Windows 路徑
`C:\Users`、LaTeX `\frac`、落單的 `\x`／`\%` 等。`JSON.parse` 直接丟
`Bad escaped character`，而 `parseJsonRobustly()`（[translate.js](../translate.js)）
原本的三段救援（直接 parse → 剝 markdown → 挖 JSON 區塊）**沒有任何一段會修復跳脫字元**，
於是整批（可能數十句）翻譯全部失敗，使用者得從頭重來。

**修正**：新增 `repairJsonEscapes()`，把「不構成合法跳脫的 `\`」逐一補成 `\\`，
並在 `parseJsonRobustly()` 末端加一段 fallback——**只在前面所有嚴格解析都失敗後才啟動**，
所以對原本就能解析的回應零影響，只會把「本來會整批丟失」的回應救回來。

```js
// 只碰「非合法跳脫」的反斜線；合法跳脫（\" \\ \n \uXXXX …）原封不動
function repairJsonEscapes(s) { /* 逐字掃描，見 translate.js */ }
```

**已驗證**（對 translate.js 抽出的真實函式跑 6 項測試，全過）：
重現原始 crash 並修復；happy path／markdown 圍欄／JSON 後綴文字／正規跳脫全部不受影響；
「35 句批次中 1 句中毒 → 整批仍救回」。

**已知取捨**：若譯文剛好是 `C:\newfile` 這種「`\` 後接 n/t」的路徑，修復會把它當成
換行/Tab（無法完美還原原意）。這在簡報／文件譯文中極罕見，且遠優於整批失敗。

**爆炸半徑**：🟡（四個 LLM 引擎共用 `parseJsonRobustly`），但因屬**純加性 fallback**，
不可能讓原本能解析的回應變差。

### M5. 測試連線成功後按「Cancel」會留下不一致狀態

**位置**：[popup.js:433](../popup.js:433) vs [popup.js:359](../popup.js:359)

`testApiConnection` 成功後**立刻**把 `apiKeyStatus: 'active'` 寫進 storage，
但 `apiKey` 本身只在按下 **Save Configurations** 時才寫入。

**重現步驟**：
1. 設定 A 金鑰 → Save（此時 storage: key=A, status=active）
2. 進設定，把金鑰改成 B → 按 Test Connection 成功 → status 仍寫成 active
3. 按 **Cancel**（不是 Save）
4. storage 現在是：`key=A`（舊的）、`status=active`（測的是 B）

結果：狀態燈說「已驗證」，但驗證的其實是另一把金鑰。若 A 已失效，
使用者會拿到一個令人困惑的翻譯失敗。

**修法**：把 `apiKeyStatus` 的寫入延後到 Save，或在 Cancel 時把 status 重設為 `unverified`。

**爆炸半徑**：🟢 低（只影響設定面板）。

### ~~M6. `host_permissions` 含萬用網域 `https://*/*`~~ ✅ 已於 2026-10-25 修正（v1.5.0）

**位置**：[manifest.json](../manifest.json)

前面已明確列出了 Google 與三家 LLM 的網域，最後又加了 `https://*/*`。
它存在的唯一理由是支援 `custom` 引擎讓使用者填**任意**端點 URL。

**風險**：Chrome Web Store 審查對萬用主機權限最敏感，
是拒審與延長審查時間的常見原因。使用者安裝時也會看到
「讀取及變更你在所造訪網站上的所有資料」這種嚇人的警告。

**修法建議**：改用 **optional_host_permissions**。
只有當使用者真的選擇 `custom` 引擎時，才用 `chrome.permissions.request()`
動態要求那一個特定網域的權限。這樣：
- 預設安裝不需要萬用權限（審查與使用者信任度都改善）
- custom 引擎功能完全保留

**爆炸半徑**：🔴 中（動 manifest + popup.js 的設定儲存流程）。

## 🟢 低優先（品質改善，不影響功能）

### ~~L1. `isTranslatable()` 的正規表示式有寫法錯誤（但實務上無害）~~ ✅ 已於 2026-10-25 修正（v1.5.0）

**位置**：[background.js:811](../background.js:811)

```js
if (/^[0-9\s\-\.,:\+\*\/%$=()\[\]{}""'']+(\s*[am|pm|AM|PM]*)?$/.test(trimmed)) return false;
```

`[am|pm|AM|PM]` 被寫成**字元集合**而不是**選擇分支**。它實際匹配的是
`{a, m, |, p, A, M, P}` 這七個字元的任意組合，作者原意應該是 `(am|pm|AM|PM)`。

我實測驗證的行為：

| 輸入 | 結果 | 是否符合原意 |
|---|---|---|
| `12:30 pm` | 跳過翻譯 ✅ | 是 |
| `2026` | 跳過 ✅ | 是 |
| `$1,500.00` | 跳過 ✅ | 是 |
| `3 mm` | 跳過 ⚠️ | 不是原意，但「3 mm」確實也不需要翻譯 |
| `Hello` | 翻譯 ✅ | 是 |

因為前面的 `[0-9...]+` 要求至少有一個數字類字元，所以純字母不會被誤擋。
**實際影響幾乎為零**，但它會誤導後續維護者。

**修法**：改成 `(\s*(am|pm|AM|PM))?$`。**改動前務必跑 Level 3 測試**——
`isTranslatable()` 是四種檔案共用的守門員。

### ~~L2. 側邊欄的固定尺寸與可調整寬度的側邊欄不符~~ ✅ 已於 2026-08-04 修正

**原問題**：[popup.css](../popup.css) 的 `body { width: 380px; height: 520px; }`
是 `action.default_popup` 彈出視窗的慣例尺寸，但本專案用的是 **Side Panel** ——
寬度使用者可拖曳調整，高度是整個瀏覽器視窗高。

我用瀏覽器實際量測到的兩個症狀：

| 症狀 | 量測結果 |
|---|---|
| **右邊沒有空隙** | 實際側邊欄約 362px 寬，但 `body` 固定 380px → body 溢出視窗 18px。`.panel` 的 `right: 20px` 是相對 380px 計算的（右緣落在 x=360），剛好貼在可見區邊界 → 左邊看得到 20px 空隙，右邊沒有 |
| **空間很大卻要滑動** | `body` 固定 520px，實際側邊欄高約 800px → 下方一大片黑色浪費。設定面板的捲動區只拿到 323px，內容需要 499px → **強迫捲動 176px** |

**修正內容**（三處，共約 20 行）：

**1. `body` 自適應視窗**
```css
html { height: 100%; }
body { width: 100%; min-width: 320px; height: 100%; }
```
`.panel` 的 `left/right: 20px` 現在相對真實視窗計算，左右自動對稱。

**2. `.panel` 改為「貼合內容」而非「撐滿高度」**
```css
.panel {
  /* bottom: 20px 已移除 */
  max-height: calc(100% - 80px);   /* 60px 上方偏移 + 20px 下方留白 */
}
```
原本 `bottom: 20px` 會強迫卡片撐滿整個高度，導致內容與底部按鈕之間出現
一大片空白（760×900 視窗下約 250px 的空洞）。改成只設 `max-height` 之後，
卡片高度由內容決定，按鈕緊跟在內容下方；內容超過可用高度時才由內層捲動。

**3. 捲動容器改用 `flex: 1 1 auto`**
```css
.settings-scroll-container, .history-scroll-container { flex: 1 1 auto; }
```
原本的 `flex: 1`（= `flex-basis: 0%`）在「高度由內容決定」的 flex 容器裡行為不可靠。
`basis: auto` 讓它在卡片貼合內容時依內容取高，在卡片觸及 `max-height` 時才收縮並捲動
（因為它有 `overflow-y: auto`，自動最小高度為 0，所以能正確收縮並保住底部按鈕）。

**修正後實測（380×820 視窗，四個面板全部左右空隙 20px、無水平溢出）**：

| 面板 | 修正前高度 | 修正後高度 | 需捲動 |
|---|---|---|---|
| 設定 | 440（強迫滑 176px） | 616（貼合內容，內容↔按鈕僅 12px） | 0 |
| 主面板（閒置） | 440 | 238 | 0 |
| 主面板（翻譯中含日誌） | 440 | 723 | 0 |
| 歷史（3 筆） | 440 | 295 | 0 |
| 檔案未偵測警告 | 440 | 304 | 0 |

**短視窗回歸測試（380×500）**：卡片正確被截在 420px（= 500 − 80），
下方留白 20px，內層捲動正常啟動（196px），Save 按鈕完整可見且仍在卡片內。

**4. 順帶修正** `.log-console-content` 的 `max-height: 80px` ——
它在高視窗下會把日誌裁切在半行的位置，改為 `clamp(80px, 22vh, 240px)`
隨視窗高度縮放（500px 視窗 → 110px；820px 視窗 → 180px；上限 240px）。

> ⚠️ **維護提醒**：不要把 `bottom: 20px` 加回 `.panel`，也不要把 `body`
> 改回固定 px —— 這兩者正是原本左右空隙不對稱與強迫捲動的成因。

### ~~L7. 停止鍵圖示在實際翻譯時錯位（macOS）~~ ✅ 已於 2026-08-06 修正

**原問題**：停止鍵（`#btn-cancel-translation`）的圖示與文字沒有垂直對齊，
但**只在實際翻譯進行中**發作；任何靜態預覽都對得好好的，因此極難重現。

**根因（找了很多輪才定位）**：`resetProgress()`（[popup.js](../popup.js)）在翻譯開始時
用 inline style 把停止鍵設成 `display: block`：

```js
btnCancelTranslation.style.display = 'block';   // ← 元凶
```

連鎖反應有兩個，剛好合成這個難查的症狀：

1. `.btn` 在 CSS 是 `display: flex`，靠 flex 的 `align-items: center` 把圖示與文字置中。
   改成 `block` 後 **flex 置中整個失效**，圖示與文字退回 inline 流排 → 錯位。
2. `block` 下，內部的 `<span>` 標籤退回 `display: inline`，而
   **`transform` 對非替換的 inline 元素完全無效**。這正是為什麼當初試圖用
   `transform: translateY()` 推文字時「設 −3 和 −39 看起來位置一樣」——
   而 `<svg>` 屬 SVG 命名空間、inline 也能 transform，所以只有圖示會動。
   這個「文字不動、圖示會動」的不對稱，是定位到 `display: block` 的關鍵線索。

> **為什麼重現這麼難**：靜態預覽從不執行 `resetProgress()`，按鈕永遠停在 CSS 的
> `flex`，所以開發環境永遠是對齊的。錯位只存在於「跑過一次翻譯」之後的實機狀態。

**修正**（兩處）：

```js
// popup.js resetProgress()
btnCancelTranslation.style.display = 'flex';   // 不是 'block'
```
```css
/* popup.css .btn —— 固定行高，避免 macOS PingFang 的 `normal` 行高偏移 */
.btn { line-height: 1.2; }
```

實測：恢復 flex 後，按鈕／文字／圖示三個中心完全重合（offset = 0），**不需要任何手動位移**。

**維護提醒**：
- 任何以 JS 顯示 `.btn` 按鈕時，一律用 `display: 'flex'`，**不要用 `'block'`**
  （會同時破壞置中與 span 的 transform）。
- 不要移除 `.btn` 的 `line-height: 1.2`——它讓文字框在各字型下維持一致高度。

**爆炸半徑**：🟢 低（只動側邊欄按鈕的顯示與排版，未碰任何邏輯與 i18n）。

### ~~L3. API 錯誤訊息直接進 `innerHTML`~~ ✅ 已於 2026-10-25 修正（v1.5.0）

**位置**：[popup.js:430](../popup.js:430)

```js
testResultMsg.innerHTML = result.message + (result.suggestion ? `<br>...` : '');
```

`result.message` 內含 `errMsg`，來源是 API 回應的 `body.error.message`
（[popup.js:216](../popup.js:216)）——也就是**遠端伺服器可控制的字串**。

一般情況下 Google/OpenAI/Anthropic 不會回傳惡意 HTML。
但 `custom` 引擎讓使用者填**任意端點**，一個惡意端點可以回傳
`<img src=x onerror="...">` 在擴充功能的特權環境裡執行 JS
（這個環境有 `storage`、`tabs`、`identity` 權限）。

嚴重度低（使用者要自己填入惡意端點，等於自我攻擊），但修起來很便宜。

**修法**：改用 `textContent` 塞訊息，`<br>` 與 suggestion 用
`document.createElement` 組出來。專案裡已經有 `escapeHtml()`
（[popup.js:1224](../popup.js:1224)）可以沿用。

### L5. `cleanUpStaleStates()` 每次啟動都讀取整個 storage

**位置**：[background.js:20](../background.js:20)

```js
const allData = await chrome.storage.local.get(null);   // 讀全部
```

它只需要 `taskState_*` 開頭的鍵，卻把所有東西讀進記憶體——

## 安全性與隱私注意事項

以下**不是 bug**，是接手時需要知道的設計取捨：

| 項目 | 現況 | 說明 |
|---|---|---|
| API Key 儲存 | `chrome.storage.local` **明文** | Chrome 的 storage.local **沒有加密**。同一台電腦上有檔案存取權的人／其他有權限的擴充功能可能讀到。這是瀏覽器擴充功能的常見做法，但值得在隱私政策裡說明 |
| OAuth token 儲存 | `activeCopies` 內含 access token，寫入 storage.local | [background.js:68](../background.js:68)。目的是取消時能刪除複本。翻譯結束會 `unregisterActiveCopy()` 清掉，但**若流程異常終止可能殘留**。建議改成只存 `copyId`，刪檔時重新取 token |
| 文件內容外傳 | 檔案裡的文字會送到使用者選定的 LLM | 這是產品的本質，無法避免。[privacy-policy.html](../privacy-policy.html) 應明確說明這一點（發布前請確認內容是最新的） |
| Client ID 內建於程式碼 | `BUNDLED_CLIENT_ID` 明文寫在 background.js | 這是**正確且必要的**做法。OAuth public client 的 Client ID 本來就不是機密，安全性由 redirect URI 白名單保證 |
| 免費引擎 | 走非官方的 `translate.googleapis.com` 網頁端點 | 沒有 SLA、可能隨時失效或被限流，且**沒有使用條款保障**。作為「無金鑰後備方案」可接受，但不該當成主要路徑推薦給企業使用者 |
