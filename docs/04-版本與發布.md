# 04 — 版本與發布

## 一、版號規則

**唯一來源：[manifest.json](../manifest.json) 的 `version` 欄位。目前 `1.7.0`。**

其他地方**全部都是讀它**，不要在任何地方寫死版號：

| 顯示位置 | 取得方式 |
|---|---|
| 側邊欄右上角徽章 | `chrome.runtime.getManifest().version` — [popup.js:5](../popup.js:5) |
| 說明頁標題旁徽章 | `chrome.runtime.getManifest().version` — [onboarding.js:5](../onboarding.js:5) |

### Chrome 的版號格式限制

Chrome 只接受 **1 到 4 段、以點分隔的整數**，每段 0–65535，**不可有前導零**。

| 寫法 | 可用？ |
|---|---|
| `1.3.0` | ✅ |
| `1.3.0.1` | ✅ |
| `1.3.0-beta` | ❌ 不接受任何非數字字元 |
| `1.03.0` | ❌ 前導零 |

**上架後版號只能往上，不能重複或倒退。** 一旦某個版號上傳過，
即使被拒審或下架，也**永遠不能再用同一個版號**。

### 語意化版號的判斷標準（建議沿用）

| 情況 | 版號怎麼跳 | 例子 |
|---|---|---|
| 改 CSS、文案、修小 bug、只動 🟢 專屬區 | 修訂號 `1.3.0 → 1.3.1` | 修 Sheets 欄寬 |
| 新增語言、新增引擎、新增檔案類型 | 次版號 `1.3.0 → 1.4.0` | 支援印尼文 |
| 改 OAuth scope、改 storage 結構、需要使用者重新設定 | 主版號 `1.3.0 → 2.0.0` | 新增 Drive Drawings 需要新 scope |

**判斷主版號的關鍵問題**：使用者升級後，需要重新做任何動作嗎？
（重新授權、重新填 API Key、歷史消失）→ 是的話就是主版號。

## 二、⚠️ `key.pem` — 最重要的一件事

```
key.pem  ← 這是擴充功能的簽章私鑰
```

### 它的作用

`manifest.json` 的 `key` 欄位是**公鑰**（[manifest.json](../manifest.json) 最後一行）。
它讓這個擴充功能在**本機開發模式**與**上架版本**擁有**完全相同的 Extension ID**。

為什麼這件事重要？因為 OAuth 的 redirect URI 是
`https://{extension-id}.chromiumapp.org/`。
如果 ID 每次載入都變，Google Cloud Console 裡註冊的 redirect URI 就會失效，登入直接壞掉。
**這正是 v1.3.0 的主要改動之一（commit `1c8ffb2` 訊息裡的 "lock Extension ID"）。**

`key.pem` 是對應那個公鑰的私鑰。

### 三條鐵律

1. **絕對不要 commit 到 git。**
   已在 [.gitignore](../.gitignore) 排除。任何時候都要確認 `git status` 沒有列出它。
2. **絕對不要弄丟。**
   遺失後你無法再產生同一個 Extension ID 的封裝。
   （上架版本本身還能靠 Chrome Web Store 帳號更新，但本機開發模式再也無法對上同一個 ID，
   OAuth 除錯會變成惡夢。）
3. **立刻備份到密碼管理器或公司的密鑰保管庫。**
   不要只留在這台筆電上。

```bash
# 確認它有被 git 排除（應該沒有任何輸出）
git status --porcelain | grep key.pem

# 確認它存在
ls -l key.pem
```

### 一起要保管的其他機密

| 項目 | 位置 | 說明 |
|---|---|---|
| `key.pem` | 專案根目錄 | 擴充功能簽章私鑰 |
| Google Cloud 專案 | Google Cloud Console | OAuth Client ID `770405736518-...` 屬於某個 GCP 專案，**你需要那個專案的存取權**才能改 redirect URI 或 OAuth 同意畫面 |
| Chrome Web Store 開發者帳號 | CWS Developer Dashboard | 上架與更新都要它（有一次性 5 美元註冊費） |

> **接手時務必向前手確認這三項的存取權。** 少任何一項都無法發布更新。

## 三、上架封裝

### 應該打包什麼

擴充功能本體只有這些（總共約 **220 KB**）：

```
manifest.json
background.js
translate.js
popup.html   popup.js   popup.css
onboarding.html   onboarding.js   onboarding.css
privacy-policy.html
icons/icon16.png   icons/icon48.png   icons/icon128.png
```

### 絕對不要打包什麼

| 不要放 | 原因 |
|---|---|
| `key.pem` | **私鑰洩漏** |
| `上架宣傳圖片/` | 11.4 MB 的商店宣傳圖。**這些是在 CWS 商店頁面另外上傳的，不屬於擴充功能本體** |
| `response_gemini_2_5.json` | 開發用的 API 回應範例，程式沒引用 |
| `.git/` `.DS_Store` | 無關檔案 |
| `docs/` `README.md` | 內部文件 |
| 舊的 `.zip` | 無關檔案 |

> ⚠️ **現有的 `workspace-translate-pro-store.zip` 有問題。**
> 我檢查了它的內容：它**包含了整個 `上架宣傳圖片/` 資料夾**，
> 導致封裝從 220 KB 膨脹到 **12 MB**（其中 11.4 MB 是用不到的宣傳圖），
> 而且還夾帶了 `response_gemini_2_5.json`。
>
> 這不會讓擴充功能壞掉，但會讓所有使用者下載 50 倍大的檔案，
> 也會增加審查時的疑慮（「為什麼一個翻譯工具需要這些圖片？」）。
> **下次發布請改用下方的打包指令。**

### 打包指令（推薦）

在專案根目錄執行：

```bash
rm -f workspace-translate-pro-store.zip && zip -r workspace-translate-pro-store.zip manifest.json background.js translate.js popup.html popup.js popup.css onboarding.html onboarding.js onboarding.css privacy-policy.html icons i18n -x ".*" -x "__MACOSX/*" -x "i18n/*.mjs" -x "i18n/package.json" -x "i18n/locales/qa.json" -x "i18n/locales/*.style.md"
```

> `i18n/` 要打包（執行期需要讀 `locales/*.json`），但其中四類是**開發專用、不可上架**：
> `*.mjs`（驗證與產生腳本）、`package.json`（只為讓 Node 認得 ESM）、
> `locales/qa.json`（偽本地化測試檔）、`locales/*.style.md`（翻譯風格指南）。
> 上面的 `-x` 已全部排除。驗證：`unzip -l` 後語系 `.json` 應為 10 個，
> `.mjs`／`.style.md`／`qa.json` 應為 0 個。

打包後**務必驗證內容**：

```bash
unzip -l workspace-translate-pro-store.zip
```

應該看到 13 個檔案、總大小約 220 KB。**如果超過 1 MB，就是打包錯了。**

### 關於 manifest 裡的 `key` 欄位

前手的做法（我從既有 zip 裡驗證過）是：**上傳到 CWS 的 manifest 移除 `key` 欄位，
本機開發用的 manifest 保留它。**

這是正確的慣例：
- 本機保留 `key` → 開發模式的 ID 與線上一致，OAuth 能正常測試
- 上傳版本移除 `key` → Chrome Web Store 用自己的簽章機制，`key` 欄位是多餘的

如果你用上面的 `zip` 指令打包，`key` 會被一起帶進去。這**通常不會被拒審**
（Chrome 會忽略它），但若想完全比照前手做法，就在打包前把 `key` 那一行暫時移除，
上傳完再加回來。

> 更安全的做法：寫一個小腳本在打包時自動剝除 `key`，避免手動改壞 JSON。

## 四、發布流程檢查表

### 發布前

- [ ] 已跑完對應等級的測試（見 [03-修改指南 §4](03-修改指南.md)）
- [ ] **Level 5 全新安裝測試已通過**（發布前必做）
- [ ] `manifest.json` 的 `version` 已遞增，且格式合法
- [ ] 若 `description` 有變，已同步更新
- [ ] `git status` 乾淨，`key.pem` 未被追蹤
- [ ] 已在 git 打 tag：`git tag v1.3.1 && git push --tags`
- [ ] **（多語系上線後）** 執行 `node i18n/validate.mjs`，所有語系必須全綠
- [ ] **（多語系上線後）** 執行覆蓋率門檻，必須 `exit 0`：
      ```bash
      node i18n/coverage.mjs --exclude onboarding --min 100
      ```
      （說明頁在 Phase 4 完成前是 0%，故以 `--exclude` 排除；Phase 4 完成後請移除該參數）
- [ ] **（多語系上線後）** 執行 `node i18n/build-manifest-locales.mjs` 重新產生 `_locales/`
- [ ] 打包並**驗證 zip 內容與大小**（約 220 KB）

### 上傳

1. 登入 [Chrome Web Store Developer Dashboard](https://chrome.google.com/webstore/devconsole)
2. 選擇既有項目 → 「套件」→ 上傳新的 zip
3. 若權限有變動，商店頁面的權限說明也要更新
4. 提交審查

### 權限變動的特別注意

`permissions` 或 `host_permissions` 有任何**新增**時：
- 審查時間會明顯變長（可能數天到數週）
- **既有使用者會看到權限警告，而且在他們手動接受之前，擴充功能會被停用**
- CWS 會要求你逐項說明每個權限的用途

目前 `host_permissions` 有一條 `https://*/*`（萬用網域）。
它存在的原因是支援 `custom` 引擎讓使用者填任意端點 URL。
但這是**審查時最容易被質疑的一項**。若遇到拒審，見
[05-已知問題](05-已知問題與技術債.md) 的建議做法。

### 發布後

- [ ] 等審查通過（狀態變成「已發布」）
- [ ] 用另一個 Chrome 設定檔從商店安裝，實測一次完整翻譯
- [ ] 確認 OAuth 授權流程正常（這是最容易在正式版出問題的環節）
