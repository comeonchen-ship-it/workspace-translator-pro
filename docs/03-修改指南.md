## 二、標準工作流程（每次修改都照這個走）

```
1. 讀 → 02-影響範圍地圖.md，確認我要改的是 🔴 還是 🟢
2. 開分支 → git checkout -b fix/描述
3. 用 grep 確認影響範圍（不要憑印象）
4. 改最小範圍
5. 手動測試（依下方分級清單）
6. 檢查 Service Worker Console 有沒有紅字
7. commit（訊息格式見下）
8. 需要發布 → 見 04-版本與發布.md
```

### 第 3 步的具體做法

```bash
grep -n "要改的函式名稱" *.js
```

看到幾個呼叫點，就是幾個要測的地方。這一步花 10 秒，能省下半天的除錯。

### Commit 訊息格式（沿用專案既有慣例）

現有兩筆 commit 使用了 Conventional Commits：

```
feat: lock Extension ID, preserve spreadsheet hyperlinks/formatting, fix form image updates
clean: remove old zip files to clean up repository
```

請延續：`feat:` 新功能 / `fix:` 修 bug / `refactor:` 重構 / `docs:` 文件 / `chore:` 雜項 / `clean:` 清理

**額外建議**：在 commit body 註明爆炸半徑，例如：

```
fix: 修正 Sheets 超連結標籤翻譯後遺失

影響範圍：僅 translateSpreadsheet()（🟢 非全域）
已測試：試算表（含 HYPERLINK 公式、局部粗體、多分頁）
```

以新增「印尼文」為例（只當**翻譯目標語言**、不做介面語系時）：

**1.** 在 [i18n/languages.js](../i18n/languages.js) 的 `LANGUAGES` 陣列加一筆：
```js
{ code: 'id', endonym: 'Bahasa Indonesia', english: 'Indonesian',
  dir: 'ltr', fallback: 'en', ui: false, target: true,
  lineHeight: 1.5, fontStack: 'latin' }
```
- `ui: false` = 只當翻譯目標，不提供這個介面語言（介面語系另需一份 `locales/id.json`）。
- `endonym` 會出現在語言下拉選單與譯本檔名（`[Translated - Bahasa Indonesia] 原檔名`）。
- `english` 會進 LLM prompt 當語言名稱。

**2.** 跑驗證：
```bash
node i18n/validate.mjs
```

**測試**：翻一份簡報，確認 (a) 下拉選單有這個語言 (b) 譯文正確 (c) 新檔名是
`[Translated - Bahasa Indonesia] 原檔名`（不是 `[Translated - id]`）。

> ⚠️ `free` 引擎走 Google Translate 網頁 API，它接受的語言代碼與這裡的 ISO 代碼
> 大多相同但**不保證完全一致**。新增語言後請用 `free` 引擎也測一次。
>
> 💡 若還要讓它成為**可切換的介面語言**（不只是翻譯目標），把 `ui` 改成 `true`
> 並新增 `i18n/locales/id.json`（140 鍵）。完整三步見 §10.7。

### 需求 D：調整 UI 外觀

**爆炸半徑：🟢 極低**

- 顏色主題：[popup.css:1](../popup.css:1) 的 `:root` CSS 變數
- 四種檔案類型的配色：[popup.css](../popup.css) 的 `body.theme-*`
- 側邊欄尺寸：`body` 現在是 `width: 100%; height: 100%`（自適應真實側邊欄大小）。
  **不要改回固定 px** —— 側邊欄寬度可由使用者拖曳，固定值會造成左右空隙不對稱
  並浪費垂直空間（原因與量測數據見 [05-已知問題 L2](05-已知問題與技術債.md)）
- 面板內縮：`.panel` 的 `top: 60px / left: 20px / right: 20px` 決定卡片與視窗邊緣的空隙。
  **左右要保持相同數值**，否則空隙會不對稱
- 面板高度：`.panel` 用 `max-height: calc(100% - 80px)` 且**刻意不設 `bottom`** ——
  卡片高度由內容決定（按鈕緊跟內容下方），只在內容過長時才由內層容器捲動。
  **不要加回 `bottom: 20px`**，那會讓卡片強制撐滿高度、在內容與底部按鈕間留下大片空洞

⚠️ 唯一風險：**改 HTML 的 `id` 屬性**。popup.js 用了 58 個 `getElementById`，
改 id 會讓對應功能靜默失效（不會噴錯，只是按鈕沒反應）。
改 id 之前先 `grep -n "那個id" popup.js`。

## 四、分級測試清單

沒有自動化測試，所以請嚴格執行手動測試。**依爆炸半徑選等級。**

### Level 0 — 純外觀（CSS、文案、onboarding）
- [ ] 側邊欄能正常打開、三個面板（主頁／設定／歷史）能正常切換
- [ ] 沒有版面破圖

### Level 1 — 單一檔案類型的專屬邏輯（🟢）
只測改動的那一種檔案：
- [ ] 該類型翻譯成功，譯本能正常開啟
- [ ] 原檔完全未被修改（**這條每次都要確認**）
- [ ] Service Worker Console 沒有紅字錯誤
- [ ] 譯本檔名是 `[Translated - 語言] 原檔名`
- [ ] 譯本落在原檔的同一個 Drive 資料夾
- [ ] 歷史清單出現這筆紀錄，點擊能開啟

### Level 2 — 單一引擎的專屬邏輯（🟢）
- [ ] 該引擎 Test Connection 顯示成功、狀態燈變綠
- [ ] 用該引擎翻譯成功
- [ ] **切換到 gemini 再翻一次**，確認沒改壞共用分派邏輯
- [ ] 故意填錯 API Key → 錯誤訊息是中英雙語的友善訊息，不是原始 JSON

### Level 3 — 🔴 共用區（`isTranslatable`、`translateTexts`、`fetchWithRetry`、`runTranslationWorkflow`、storage keys）

**四種檔案類型全部都要測**，而且要用有內容深度的測試檔：

| 檔案類型 | 測試檔至少要包含 |
|---|---|
| **Slides** | 3 頁以上、表格、群組圖形、演講者備忘稿、超連結、純數字頁碼 |
| **Docs** | 頁首頁尾、註腳、表格、超連結、email 地址、項目符號清單 |
| **Sheets** | 2 個以上分頁、`=HYPERLINK("url","標籤")` 公式、局部粗體的儲存格、公式儲存格、數字欄 |
| **Forms** | 選擇題、量表題（含高低標籤）、方格題、含圖片的題目、確認訊息、測驗答案 |

四種都要驗證：
- [ ] 翻譯成功且**版面沒有跑掉**
- [ ] **所有超連結仍然可以點擊，且指向原本的網址**（這是 `isTranslatable` 的核心職責）
- [ ] email 地址沒有被翻譯
- [ ] 純數字（頁碼、金額、日期）沒有被翻譯
- [ ] 原檔完全未被修改

### Level 4 — 佇列 / 取消 / 生命週期（🔴🔴）
- [ ] **併發**：同時開 3 個檔案分別按翻譯 → 前 2 個執行，第 3 個顯示「Waiting in queue #1」
- [ ] **佇列遞補**：第 1 個完成後，第 3 個自動開始，排隊號碼正確更新
- [ ] **取消**：翻譯中按 Stop → 停止，且**已複製的 Drive 檔案被自動刪除**（去 Drive 確認沒有殘留檔）
- [ ] **關分頁**：翻譯中把原檔分頁關掉 → 任務被取消，下一個佇列任務接上
- [ ] **關側邊欄**：翻譯中關掉側邊欄再打開 → 進度**從 storage 還原**，繼續顯示
- [ ] **SW 重啟**：翻譯中在 `chrome://extensions` 按重新載入 ⟳ → 再開側邊欄應顯示
      「Translation interrupted by browser or extension restart」的友善訊息
- [ ] **快取**：翻譯同一份檔案兩次 → 第二次日誌顯示「Cache Hit」且明顯更快
- [ ] **切換檔案**：在檔案 A 翻譯中切到檔案 B 分頁 → B 的進度區是乾淨的，不會顯示 A 的進度
- [ ] **非 Google 分頁**：切到 google.com 或任意網站 → 顯示警告面板（不是空白或壞掉）
- [ ] **語言記憶**：對檔案 A 選日文、檔案 B 選韓文 → 來回切換分頁，各自記住自己的語言

### Level 5 — 全新安裝（發布前必做）
```js
chrome.storage.local.clear()
```
然後移除擴充功能、重新載入未封裝項目：
- [ ] 設定畫面是預設值（gemini + `gemini-3.1-flash-lite`）
- [ ] 未設定 API Key 就按翻譯 → 彈出「API Key Required」提示視窗
- [ ] 填了 Key 但沒按 Test Connection 就翻譯 → 彈出「API Key Not Verified」
- [ ] 首次翻譯會出現 Google OAuth 授權視窗，授權後正常完成
- [ ] 說明頁（Help）能正常開啟，Redirect URI 能正確顯示與複製

## 六、重構時的優先順序建議

若有時間做技術債清理，建議這個順序（**風險由低到高**）：

| 順序 | 做什麼 | 風險 | 效益 |
|---|---|---|---|
| 1 | 刪掉 dead code `duplicatePresentation()`（[background.js:651](../background.js:651)，無人呼叫） | 極低 | 減少誤用 |
| 2 | 把重複四次的 system prompt 抽成一個常數 | 低 | 消除地雷 #2 |
| 3 | 把語言清單抽成單一來源（新增 `constants.js`，讓 translate.js 與 background.js 共用） | 低 | 消除地雷 #1 |
| 4 | 統一 Gemini 預設模型（popup.js 與 translate.js 目前不一致） | 低 | 消除困惑 |
| 5 | 收緊 `host_permissions`（移除 `https://*/*`） | 中 | 降低上架審查風險，但會限制 custom 引擎 |
| 6 | 把 `handleTabChange()`（近 190 行）拆成偵測 + 渲染兩部分 | 中 | 可讀性 |
| 7 | 把 `background.js`（1784 行）拆成多個 ES module | 高 | 可維護性，但一次動到所有共用區 |

**不要一次做完。** 每項獨立 commit，每項都跑對應等級的測試。
